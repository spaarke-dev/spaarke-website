## Why the table exists

One column carries the value: provenance. A turn the assistant answered from
general knowledge is a subject the library does not cover, and read under the
article the reader was on it is the brief for the next piece. Everything else in
the row either makes that column legible or keeps the row inside the retention
window.

## The table

The table is `InsightsConversations`, in the existing website storage account:

| Key | Value | Why |
|---|---|---|
| `partitionKey` | UTC date, `YYYY-MM-DD` | Both jobs are time ranged |
| `rowKey` | `${Date.now()}-${8 hex chars}` | Sortable within the day, collision safe |

The date partition is the one deliberate design choice in the schema. The purge
takes everything older than the window and the report reads the last few weeks,
so a date partition makes each a key range scan rather than a table scan. A
`YYYY-MM-DD` string compares lexicographically the way it reads, so `lt` and `ge`
on the partition key mean what they say about time. A marketing site's write
volume is nowhere near what a single partition will take.

| Property | Type | Notes |
|---|---|---|
| `question` | string | What the reader typed. Blanked by the purge |
| `articleSlug` | string | The article the reader was on. Empty when none |
| `provenance` | string | `corpus`, `general`, `mixed` or `contact` |
| `citedSlugs` | string | Comma joined, empty when the answer cited nothing |
| `continued` | boolean | True when the turn was not the first in its session |
| `askedBack` | boolean | Whether the assistant asked the reader a question |
| `sessionId` | string | Client generated, ephemeral, groups turns into a conversation |
| `answerChars` | number | Length of the assembled answer |
| `errorCode` | string | The `InsightsErrorCode`, empty on success |
| `createdAt` | string | ISO timestamp |
| `purged` | boolean | False at insert, true once the question text is gone |

Table Storage has no useful null, so an empty string is the absent value
throughout: no article, no citations, no error.

`purged` is written false at insert rather than left off, because Table Storage
matches nothing on a property a row does not carry. A row inserted without the
flag would be invisible to the purge forever, so anything written by hand has to
carry it too.

## What is deliberately not recorded

No IP address and no IP hash. No name, no email, no user agent, no referrer.
Nothing that identifies a reader, and nothing the site does not already collect
elsewhere.

The session id is generated by the client for the life of one page. It is not a
cookie, it is not persisted anywhere, and it survives neither a reload nor a
second tab. It groups turns into a conversation, which is what `continued` is
read against, and it identifies nobody.

Readers will type confidential things into an assistant however plainly they are
asked not to. That is the argument for a short window and a narrow column set. It
is not an argument for capturing less of the signal the feature exists to
produce.

## Retention, and how the purge runs

Ninety days, then the question text goes and the row stays. The purge blanks
`question` and sets `purged`, using a merge rather than a replace, so every
aggregate column survives and a count taken over a year of data is still right.
It deletes no rows, and it runs two ways.

**Sampled from the write path**, roughly one write in fifty. There is no
scheduler and no cron secret for storage in this repo, and putting a promise the
privacy policy has already made behind new infrastructure is how the promise ends
up unkept. Sampling needs none: at one write in fifty the sweep runs several
times a day at any traffic worth reporting on, and at no traffic there is nothing
arriving that needs purging. It is awaited, because the serverless function can
be frozen the moment the response resolves, and it swallows every failure,
because a reader's answer must never depend on a sweep.

**By hand or from a workflow**, through the exported function.

```ts
import { purgeOldQuestionText } from "@/lib/insights/capture";

const changed = await purgeOldQuestionText();      // the 90 day window
const forced = await purgeOldQuestionText(30);     // a shorter one, for a test
```

It returns how many rows it changed, and running it twice returns zero the second
time.

## The content gap report

```
npx tsx scripts/content-gap-report.ts             the last 30 days
npx tsx scripts/content-gap-report.ts --days 90   the whole retention window
```

Reads `STORAGE_ACCOUNT_CONNECTION` from `.env.local`, or from the environment if
it is not in the file. Four sections, on stdout:

1. Turn count, sessions, follow-up count, and the split by provenance.
2. **Questions answered from general knowledge, grouped by the article the reader
   was on, with the question text.** This is the report. Each line is a question
   the library could not answer.
3. The same for `mixed`, which is the weaker version of the same signal: the
   articles covered part of the question.
4. The articles generating the most questions, and the turns that ended in an
   error by code.

A window longer than 90 days reports counts with no text against its oldest
days, and the heading of each group says how many of its questions are past
retention. That is the retention mechanism working, not a bug in the report.

A missing table and an empty window both say so and exit cleanly. The table is
created by the first write, so a missing table means nothing has been recorded
yet.

## What the public endpoint can do with this store

Write, and nothing else. The route calls `recordTurn` and never reads. There is
no read path, no API surface over the table, and no route that takes a partition
key. The report is a local script run against the connection string, which lives
in app settings rather than in anything a browser can reach.
