# Implementation Plan: Article Insights Assistant

> Derived from `spec.md`. Phases, deliverables, and the acceptance gate for
> each. Generated by `project-pipeline` on 2026-09-25.

## Shape of the work

Five phases. The ordering is deliberate: the two things most likely to be
wrong are the prompt and the cost model, so both are proven before any
interface is built on top of them.

Phase 0 stands up the Foundry path and measures what a real call costs.
Phase 1 builds the corpus and the prompt, and puts an evaluation runner
around them, so answer quality is measurable before a reader ever sees it.
Phase 2 adds the endpoint with its cost and abuse defences. Phase 3 builds
the two interface surfaces. Phase 4 instruments, then launches.

The reason the evaluation set comes before the interface is that a console
that looks finished invites shipping. If quality is only assessed once the
UI exists, the pressure is to ship anyway.

## Phase 0: Foundation and cost truth

**Deliverables**

- Website-specific Foundry project with a Claude deployment, separate from
  the product's Foundry resources
- App settings wired into Azure Static Web Apps
- A throwaway script that makes one real call and reports token counts and
  measured cost, including a cache hit and a cache miss
- A decision, written down, on Entra ID versus API key

**Gate.** A real call succeeds from a server-side context, and the measured
per-turn cost at roughly 100,000 cached input tokens is recorded against
the 500 USD monthly ceiling. If the arithmetic does not work, the design
changes here rather than after the interface exists.

**Risk this retires.** NFR-01 is currently sized on an estimate. Every rate
limit downstream depends on the real number.

## Phase 1: Corpus, prompt, and evaluation

**Deliverables**

- Build-time corpus manifest from `content/blog/`, with a logged token
  count and a build failure above a configured ceiling
- System prompt carrying labeled provenance, the citation format, the
  register, and Spaarke's stance from `voice/stance.md`
- Suggested questions generated per article from frontmatter
- Evaluation runner plus 30 to 50 cases, runnable on demand

**Gate.** The evaluation suite runs and reports per case. Cross-article
cases pass. Provenance labeling is correct on corpus-only, knowledge-only
and mixed questions. Citations resolve to real anchors.

**Risk this retires.** That the assistant contradicts the articles it
quotes, which is the failure that would cost the most credibility.

## Phase 2: The endpoint

**Deliverables**

- Streaming route at `src/app/api/article-insights/`
- Durable per-IP counter, since the existing in-process limiter resets on
  every function recycle
- reCAPTCHA on the first question of a session, reusing the site's keys
- Per-session cap and a global daily ceiling that degrades the feature
  rather than the budget
- Conversation capture in Table Storage with 90-day retention
- Hard timeout with an error that names the failure

**Gate.** A scripted client with no captcha token cannot reach the model. A
forced hang produces a visible error rather than an open stream. The global
ceiling, when tripped, disables the console with an explanation.

**Risk this retires.** An unmetered public endpoint calling a frontier
model. This phase is what stands between the feature and a surprise bill.

## Phase 3: The interface

**Deliverables**

- Right-rail console on article pages, in the region the layout leaves empty
- Mobile bottom sheet behind a floating button
- Entry card with three extending questions, summarize offered after them
- Citation chips linking to `{slug, heading, anchor}`
- Linked summary, where each claim points at the section arguing it
- Persistent disclaimer in the console chrome
- Assistant-initiated questions, skippable, one at a time

**Gate.** Usable one-handed at 375px and correct at 1440px. Keyboard
operable with focus managed. The disclaimer is present in the first
rendered state on both surfaces. Summarize is never the first option
offered.

**Risk this retires.** That the console teaches readers to skip the
article. The entry-point ordering is the control, which is why it is an
acceptance criterion rather than a preference.

## Phase 4: Instrument and launch

**Deliverables**

- Telemetry for open, question, provenance, citation-follow and error
- Comparative scroll depth and time on page, assistant users against others
- First content-gap report from the question log
- Azure cost alert below the monthly ceiling
- Rollout across all 21 articles

**Gate.** Events confirmed arriving in Application Insights, which cannot
be assumed given telemetry was dropping nearly everything until the flush
fix of 2026-09-25. The comparative measure has a baseline before launch.

**Risk this retires.** Shipping something whose effect cannot be judged. If
the assistant reduces engagement, only measurement will show it.

## Milestones

| Milestone | Phase | Means |
|---|---|---|
| M1 Cost proven | 0 | A real call, measured, inside the ceiling |
| M2 Quality proven | 1 | Evaluation suite passing |
| M3 Endpoint safe | 2 | Bot and spend defences demonstrated |
| M4 Surfaces complete | 3 | Both viewports, accessible |
| M5 Measurable | 4 | Events arriving, baseline captured |

## Dependencies between phases

Phase 0 blocks everything: nothing can be called until the deployment
exists. Phase 1 depends on Phase 0 only for the model call in the
evaluation runner, so manifest and prompt work can start in parallel.
Phase 2 depends on Phase 1 for the prompt it serves. Phase 3 depends on
Phase 2 for the stream it renders. Phase 4 depends on Phase 3 for the
events it measures.

## Risks carried from the spec

**Cost sizing rests on an estimate** until Phase 0 measures it. Every rate
limit is provisional until then.

**The existing rate limiter is unsuitable.** `src/lib/rate-limit.ts` holds
counters in a module-level `Map`, so it resets on recycle and is not shared
across instances. Adequate for contact-form spam, useless as a spend guard.

**Substitution is unproven.** Whether the assistant deepens engagement or
replaces reading is genuinely unknown, which is why Phase 4 establishes a
baseline rather than assuming the answer.

**Zero Data Retention.** If the Azure subscription has ZDR enabled,
Anthropic's Covered Models reject requests. Microsoft cannot change it.
Surfaces in Phase 0 or not at all.

## Out of scope for this project

Retrieval, chunking, and vector stores. Reuse of the Spaarke BFF chat path.
The library-wide console surface. Structured multiple-choice questions.
Authenticated or personalized sessions. All are release two or later.
